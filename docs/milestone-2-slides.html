The big picture

Sources turn their registry's data into TrialRecords. Everything else talks to one storage interface, and the SQLite backend behind it owns the files, the schema and search.

One record for every registry

TrialRecord is what a source produces and storage keeps: a plain dataclass, abridged here. The rules around it matter more than the fields.

@dataclass(slots=True, kw_only=True)
class TrialRecord:
    source: str                # "ctgov"
    source_id: str             # "NCT05026866"
    title: str
    official_title: str | None
    status, phase, study_type, primary_purpose
    start_date … last_update   # five dates
    enrollment, enrollment_type, arms_count, has_results
    min_age_days, max_age_days, sex, healthy_volunteers
    brief_summary, description, eligibility_criteria
    outcomes:      list[Outcome]
    conditions:    list[str]
    mesh_terms:    list[MeshTerm]
    interventions: list[Intervention]
    sponsors:      list[Sponsor]
    countries:     list[str]        # ISO alpha-2
    locations:     list[Location]
    raw:           bytes | None     # the source's JSON
    content_hash:  bytes | None
    id:            int | None       # storage sets
    ingested_at:   datetime | None  # storage sets

    # properties, derived from the lists
    lead_sponsor · location_scope · num_sites

One vocabulary

Coded fields use ClinicalTrials.gov API v2's codes: RECRUITING, PHASE2_PHASE3, INDUSTRY. Another registry maps its own codes onto them.

Identity

An integer id for fast joins, plus a unique (source, source_id), so a second registry fits beside ClinicalTrials.gov.

Values, not strings

Dates are dates (a month-only date becomes the 1st), ages are days, countries are ISO codes. Filters become plain comparisons; v1 kept ages as text.

Lists keep their order

Storage returns each list in the source's order. A repeat (the same condition, sponsor, or MeSH code and kind) collapses to its first occurrence.

Derived, never stored twice

Lead sponsor, location scope (US, NON_US, BOTH) and site count come from the lists. Storage copies them into trials for filters.

A plain dataclass

slots=True keeps 607k of them cheap to build in worker processes. Pydantic models appear only at the API edge, in milestone 4.

The storage contract

Code above storage talks to the Storage protocol, never to SQLite directly. Writes come in three sizes, and a shared test suite pins down how any backend must behave.

Reads and search

  • get_trial(id)a record
  • find_trial(source, source_id)a record
  • query_trials(query)list rows
  • count_trials(query)a count
  • search(text)best first
  • lookup_names(text, kind)names

Lists read only trials and page with after_id, not OFFSET. Milestone 4's TrialFilter adds the rest.

upsert_batch one-off

Runs in its own transaction. Returns ids in input order; an existing trial keeps its id and is replaced whole.

transaction() updates

BEGIN IMMEDIATE. Upsert, read your own writes, and write other tables on tx.connection: all commit together or not at all.

bulk_load() install

Each batch commits on its own; indexes and search are rebuilt at the end. Meant for a new file nobody else is reading.

with storage.transaction() as tx:        # BEGIN IMMEDIATE: take the write lock now
    ids = tx.upsert_batch(changed_trials)
    tx.connection.execute(log_changes)   # the change log, in the same transaction
    tx.connection.execute(bump_version)  # meta.data_version too
# commits here; any exception rolls all of it back. Milestone 3's update does exactly this.

The tables

Everything hangs off trials by trial_id. Names are stored once and linked; text, raw documents and search indexes sit apart, so the table every filter scans stays narrow.

A reverse index for filters

Each link table has one, ready for milestone 4's filters and facets. Bulk loads drop it and build it at the end.

Writing a batch of trials

An upsert runs inside the caller's transaction, a whole batch per statement, in an order the full-text index depends on.

Prepare

1 · Check

drop repeats in each list; one record per trial; every country code must be known, or ValueError and nothing is written

→

2 · Match ids

look up (source, source_id); new trials take max(id) + 1, safe because the write lock is held

→

3 · Resolve names

get or create conditions, interventions, sponsors and MeSH codes, one query each per batch

Write

4 · Unindex old text

delete existing trials' rows from trials_fts first, while their old text is still there

→

5 · Replace rows

update trials in place (id and change history kept); delete and re-insert text, outcomes, documents, links and sites

→

6 · Index new text

insert trials_fts rows from the content view; add new names to names_fts

Why step 4 comes first

FTS5 deletes a trial's words by re-reading its text through the view. Done after the text changes, it removes words that aren't there and corrupts the index. Tests run FTS5's integrity check after updates.

One parameter, any batch size

Id lists go as one JSON array, id IN (SELECT value FROM json_each(?)), rather than 5,000 bound values.

Bulk loads skip 4 and 6

They redo both in one pass at the end, and keep every name's id in memory across batches instead of querying for it.

Two full-text indexes

trials_fts finds trials by the words in them; names_fts finds condition, intervention and sponsor names from a fragment. Both are SQLite FTS5.

trials_fts: words, ranked porter · unicode61

Nine columns, ranked by bm25 with these weights, so a word in the title counts ten times one in the eligibility criteria:

names_fts: names by fragment trigram

Matches anywhere in a name and ignores case and accents: zheim finds Alzheimer Disease, universite lyon finds Université Claude Bernard Lyon 1. Shorter names come first. Milestone 4 uses it to pick filter values.

Queries are plain words

Each word is quoted, so NOT, *, ( and title: are just text, and every word must match. Stemming makes infusion, infused and infusions the same word.

Keeping the index honest

The index stores no text: it reads it through the view, which must return identical text every time (group_concat(… ORDER BY position)). FTS5 can't read json_each through a view, so outcomes became rows. Tests run FTS5's integrity check against the view.

Connections, migrations and doctor

Every connection is set up the same way, every schema change is a numbered migration, and trial-al doctor checks it all before anything runs.

Every new connection

  1. sqlite3's own transaction handling is switched off; SQLAlchemy sends BEGIN, or BEGIN IMMEDIATE for writes
  2. seven PRAGMAs:
    WALsynchronous NORMALforeign keys on5 s busy timeouttemp in memory64 MB cache1 GB mmap
  3. each plugin's extension: enable_load_extension(True), load(conn), then (False), so SQL itself can never load one
  4. one connection opens at startup, so an extension that fails stops startup, naming the plugin

Migrations, per component

  • _migrations(component, version) in each file: the core, then each plugin, numbered 1, 2, 3…
  • Each runs in its own BEGIN IMMEDIATE: a failure leaves nothing half-done, and two processes starting at once can't both apply it.
  • Running again applies nothing; a database from a newer version is refused.
  • Released migrations are frozen SQL. test_schema checks them against the SQLAlchemy tables, column by column.
  • Plugins add theirs with add_migrations("trials" | "app", …); they run after extensions load.

Already used: milestone 3 shipped core migration 2 (compressed documents, four more countries), and milestone 2 databases upgrade when opened.

Decisions, and what came next

What milestone 2 settled, what milestone 3 has changed since, and what's still open.

Settled in milestone 2

  • Plugin state stays in trial-al.toml. app.db has no plugin_state; design §3, §5.6, §5.9 and §6 say so.
  • Outcomes are rows, because FTS5 can't read json_each through its view.
  • Names once, details on the link, so every record reads back exactly.
  • No separate phase index: (phase, status) serves both.
  • Writes lock up front with BEGIN IMMEDIATE and wait up to 5 s.
