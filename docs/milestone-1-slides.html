The whole system, and where milestone 1 sits

v2 is one Python package, the core, plus plugin packages. Milestone 1 built the frame the rest hangs on: the plugin loader, config and the CLI. Colored boxes are milestone 1.

built in milestone 1 built in milestones 2–3 still to come (M4–M6)

A minimal core; everything else is a plugin

Plugins depend on the core, never the other way round. The core finds them at runtime and meets each one at a single object, the registry.

The core never imports a plugin

At startup it reads the entry-point group tri_al.plugins. Installing a package is enough; no list of plugins lives in the core.

Plugins use only core interfaces

Plugin, Registry, and what they register: a source, migrations, CLI commands, event handlers. Plugins talk to each other through events.

Each plugin owns its tables

Prefixed table names and its own migrations, tracked under its name. Disabling a plugin leaves its tables where they are.

One repository, two generations

v2 is a uv workspace sitting beside v1's Django code on the same branch. One command, uv sync, sets up the core, the plugins and the tools; v2's tools ignore v1's files.

A virtual root

The root pyproject.toml is no package of its own. Its dev group pulls in both workspace members plus ruff, mypy and pytest, so uv run tri-al works with no flags.

Each package stands alone

core/ and every plugins/* has its own pyproject.toml, src/ layout and tests, built with uv_build. Plugins depend on tri-al, never the reverse.

Python 3.13, uv-managed only

python-preference = "only-managed": macOS's own Python can't load SQLite extensions, which storage needs (design §5.2).

v1 stays put

No v1 file moved or deleted. ruff, mypy and pytest are scoped to v2; v1's self-hosted deploy workflow is unchanged.

How the core loads plugins

At every start the core finds the installed plugins, checks the enabled ones, puts them in order, and only then lets them register. A problem anywhere stops the start, with the whole list.

Load order, and what errors look like

requires lists plugins that must load first. Every check produces one plain line naming the plugin and, where it can, what to do about it.

  • Other APIalpha: written for plugin API 2, but this tri-al supports API 1; upgrade the plugin or tri-al
  • Disabled needc: requires plugin 'nope', which is disabled; run `tri-al plugins enable nope`
  • Missing needc: requires plugin 'nope', which is not installed
  • Cyclea: requires form a cycle: a -> b -> a
  • Bad settingsample: invalid setting greeting: Input should be a valid string
  • Stray settingalpha: takes no settings, but [plugins.alpha] sets colour
  • Import failsalpha: failed to import alpha_pkg:plugin: ModuleNotFoundError(…)
  • Same name twicealpha: other-pkg 1.0 also provides a plugin with this name; uninstall one of them
  • register() raisesalpha: register() failed: … stops at once

What a plugin looks like

A package with one entry point, which names a Plugin object. The core calls its register function with a registry scoped to that plugin, holding its validated settings.

plugins/sample/pyproject.toml[project.entry-points."tri_al.plugins"]
sample = "tri_al_sample:plugin"
plugins/sample/src/tri_al_sample/__init__.py (abridged)class Settings(BaseModel):
    model_config = ConfigDict(extra="forbid")
    greeting: str = "Hello"

def register(registry: Registry) -> None:
    settings = registry.settings
    assert isinstance(settings, Settings)
    cli = typer.Typer()
    @cli.command()
    def hello(name: str = "world") -> None:
        typer.echo(f"{settings.greeting}, {name}!")

    registry.add_cli(cli)

plugin = Plugin(
    name="sample",
    version=version("tri-al-sample"),
    api_version=1,   # a literal, not the core's constant
    register=register,
    settings=Settings,
)

Plugin fields

  • namematches the entry point; lowercase, digits, _
  • api_versionmust equal the core's plugin API, now 1
  • requiresplugins that must load first
  • settingsPydantic model for its config section
  • registercalled once, with its registry
  • versionwith description, shown by plugins list

Config: one file, with the environment on top

Defaults live in the code, tri-al.toml changes them, and TRI_AL_* variables override both. Everything is validated, and an error says where a bad value came from.

tri-al.toml[server]
port = 9000

[plugins.sample]
greeting = "Hi"
environmentTRI_AL_SERVER__PORT=9100

server.port: Input should be a valid integer, … (from TRI_AL_SERVER__PORT)

plugins enable|disable edits the file with tomlkit and keeps its comments. Changes apply on the next start.

The tri-al command

The command is assembled at every start: core commands first, then a group for each enabled plugin that adds one. If plugins can't load, the core commands still work, so you can see why and fix it.

Milestones 2–3

From plugins

sample hello

A stub prints tri-al serve: not implemented yet and exits with code 1, so a script can't mistake it for success. Plugin groups appear under their own "Plugins" heading in --help, and a plugin can't take a core command's name.

Decisions made, and what's still open

The first four were choices the design left open; later milestones kept them. The rest are small and none blocks anything.

1Installed means enabled. A plugin loads unless its section says enabled = false; enabled is reserved in every plugin section.decided · milestone 1
2On/off state lives in tri-al.toml, not a database. Changes apply on the next start.decided · confirmed in M2
3The plugin API version must match exactly (an integer, now 1). Plugins write the number, not the core's constant, or the check could never fail.decided · milestone 1
4Fail at startup, with every problem at once, but keep core commands working so the problem can be seen and fixed.decided · milestone 1
5"Secrets only from the environment" (design §5.7) isn't enforced: a secret written in the file would be accepted.open · later
