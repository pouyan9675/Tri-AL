The big picture

Two processes, three files, one writer

tri-al serve starts the API and one job worker. The API only reads trials.db; the job worker is its only writer. Progress goes to app.db, a different file, so it stays visible while an update holds trials.db's write lock.

Plus tri-al.toml: plugins on or off and their settings, read at startup (edited by PATCH /api/plugins/{name}).

Progress, at most twice a second

The pipeline reports often; JobProgress writes the job's row at most every 0.5 s, and its heartbeat thread writes a held-back report a moment later, so each stage's end still shows.

One data job at a time

Install, update and rebuild exclude each other: in the queue, in claim, and with a unique index. tri-al update in a shell records a job too, so the UI shows it and won't start another.

Crashes, cancels, schedule

A job whose heartbeat is quiet for 60 s is failed when a worker starts. Cancel stops at the next report and rolls back. The schedule queues an update daily (or off, hourly, "daily at 06:30"…).

What's stored where, at what size

Text is kept once now, compressed

Milestone 3 stored every summary, description, eligibility text and outcome twice: in the raw documents and as plain columns the search index read through a view. Migration 3 made the index contentless and packed each trial's text into one zstd blob (your choice over raw documents only, so storage still returns whole trials without the source plugin).

The conversion

Migration 3 on your database: 4m24s. VACUUM INTO a compact copy: 42 s. Checks on the copy (quick_check, the index's integrity check): 74 s. Runs and change log kept.

New in trials.db

  • stats: 17 rows, 0.1 MB (7 charts, 10 facets)
  • doc_dicts: a second dictionary, for text
  • gone: trial_outcomes, the index's view

In memory, per API worker

  • trial index: 58 MB, rebuilt in 2.6 s per data version
  • result cache: up to 64 MB, keyed by data version

The search rework

Find candidates, rank the newest, unpack only the winners

Ranking scores every match (about 2 µs each), so a word in nearly every trial took 1.5 s. Now a search ranks at most the 20,000 most recently registered matches, exactly as before when fewer match, and builds snippets from the top hits' text alone.

Whole search request now, vs ranking alone before

  • "study" · 572k matches1,495 → 79 ms
  • "patients" · 459k905 → 83 ms
  • "cancer" · 156k283 → 70 ms
  • "alzheimer" · 9.5k, ranked exactly29 ms
  • "donepezil" · 717, ranked exactly10 ms
  • "the" · in nearly everything103 ms

Now includes snippets and name suggestions for ⌘K (capped the same way: "the" sat in a fifth of all names and took 76 ms to sort). Hits say capped when more matched than were ranked.

How a request is served fast

Skip work first, then count in memory

  • 1 Host and header checksµs
  • 2 Open one read snapshot, read its data version
  • 3 ETag matches? → 3040.6 ms
  • 4 No filter? → the stored chart, as bytes0.8 ms
  • 5 Asked before for this data version? → cache< 1 ms
  • 6 Filter → numpy mask → counts2–40 ms
  • 7 Index still building? → SQLite~3 s after a start or update

The trial index holds what filters, facets and charts use: coded columns, dates, enrollment, and the condition, intervention, sponsor and country links of all 607k trials. It agrees with SQLite exactly; the tests compare every count and every page.

The work is visiting hundreds of thousands of link rows, which no SQL shape or index avoided (threads were slower still). Hence numpy as a core dependency: decision 13.

Measured against design §10

Every API target met, on all 607,349 trials

Over HTTP to a real uvicorn server, server time from the Server-Timing header. Filters and searches are cold: 32 filters (rare to nearly everything, alone and combined) and 30 queries, each asked once.

The slowest single request: the list for q=study, 150 ms, which has to ask the full-text index for 572k matching ids. Numbers and method: bench/README.md, bench/api_bench.py.

Access

No login, but other websites can't press Update

Anyone who can reach the server may do everything, as decided. It listens on 127.0.0.1 unless told otherwise (then serve and doctor warn). Three browser checks stay on regardless, and every route asks one require(action) hook, which an auth plugin could replace without touching a route.

1Host must be one of the server's names, on every request: a DNS-rebinding page (evil.example → 127.0.0.1) gets 400. Other names go in server.allowed_hosts.reads too
2X-Tri-AL header on requests that change something. Another origin can't add it without a CORS preflight, which the server never approves.POST · PATCH · …
3Origin, when present, must be one of the server's names; Sec-Fetch-Site: cross-site is refused.POST · PATCH · …
4require(action): read, jobs.update, jobs.cancel, plugins.edit. The core's policy allows all; registry.set_access_policy swaps it.every route
