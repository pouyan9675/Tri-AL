The big picture

Data flows one way: from ClinicalTrials.gov, through the plugin and the core pipeline, into trials.db. Only the plugin knows ClinicalTrials.gov's JSON layout.

Two ways in: install and update

Same stages, different fetch. An install builds a new database file and swaps it in; an update changes the existing one in a single transaction.

What trials.db holds

Everything ClinicalTrials.gov publishes is kept once, compressed. Most of the 9.1 GB is copies built for speed: plain text for search, the search indexes, and structured tables.

Original documents

Every study's full JSON, byte for byte, compressed to 19% with zstd. The only place results, arms, design details, contacts and references live.

One narrow row per trial plus links to conditions, MeSH, interventions, sponsors, countries and sites, for filters and charts.

The tables

Everything hangs off trials by trial_id. Names (conditions, sponsors…) are stored once and linked; per-trial details sit on the link.

Why the text is stored twice, and how to stop

Today's full-text index stores only word positions and reads the text back through SQL whenever it needs it. SQL can't unpack compressed documents, so the text has to be plain.

Today: the index reads its text external content

It reads the text to:

  • remove a trial's old words when an update changes it
  • rebuild the whole index after the install's bulk load
  • make snippets and highlights, and run its integrity check

Your idea, for milestone 4 contentless

  • the pipeline hands the index the text as it writes each trial
  • matching, phrases and ranking work from the index alone
  • SQLite 3.43+ can update and delete without the old text
  • no plain copies: about 5.3–6.4 GB instead of 9.1

How an update knows what changed

Each trial stores a fingerprint of its study. An update fingerprints what it fetched and writes only the studies whose fingerprint differs.

Why drop the release date

Hashing it would make every study the update fetches look changed, every day: thousands of pointless rewrites and false "updated" events. The plugin decides what to leave out (hashable).

The cursor and the overlap

meta keeps the latest update date seen (2026-10-16). The next update asks from one day earlier, because dates have no time of day. The fingerprint makes the overlap free: today all 2,606 refetched studies were skipped.

The change log

For changed trials, trial_changes records old and new values of tracked fields: status, phase, dates, enrollment, lead sponsor, conditions, interventions, countries, sites… It replaces v1's history tables; a field's first value is the "old" of its first change.

What keeps the data safe

Readers never see half-written data, a failure leaves things as they were, and a re-run picks up where the last one stopped.

Updates are all or nothing

One BEGIN IMMEDIATE transaction holds the trials, change log, cursor and data version. Readers see the old data until it commits. A failure writes nothing and marks the run failed.

Installs build beside the old database

The new data goes into trials.db.new, gets checked, then is renamed over trials.db. Install refuses to replace an existing database without --force, or one another process has open.

Interrupted? Run it again

Each install stage is checkpointed in runs. A re-run skips finished stages and trials already loaded with the same fingerprint, and reuses a finished download. (The server doesn't support resuming a half-finished download.)

One bad study doesn't stop 600k

A study that fails to parse or normalize is skipped and counted, with the first 100 messages in the run summary (0 of 607,349 failed). Plugin event handlers run after commit; one that crashes is logged and doesn't stop the run.

Who owns what

The core knows trials, storage and the pipeline; the plugin knows ClinicalTrials.gov. They meet at a small interface that any future registry can implement.

Core (trial-al)

  • TrialRecord: the shape every source produces
  • Storage: SQLite tables, migrations, compression, search
  • Pipeline: install, update, fingerprints, checkpoints, change log, events
  • CLI: install, update, doctor, plugins

The interface: Source

  • fetch_all(ctx) → raw JSON
  • fetch_changed(since, ctx)
  • normalize(raw) → TrialRecord
  • hashable(raw)

Checked by the SourceContract test suite.

ctgov plugin (trial-al-ctgov)

  • Download the zip; page the API; back off on 429 and 5xx
  • Read the zip without extracting it
  • Normalize: phases, dates, ages, 226 countries, MeSH, sponsors, outcomes, sites
  • Leave versionHolder out of the fingerprint
